# MAGNT Owner — включение B.1 без Zero Trust

Адрес личного MCP: **`https://owner.magnt.ru/mcp`**. GitHub подтверждает владельца
при подключении; затем ChatGPT обновляет доступ токеном MAGNT без нового входа
в GitHub. Доступ истекает после 30 дней без обновления и может быть отозван.

Выпуск читает обращения и цели, сохраняет частные черновики, отмечает и архивирует
входящие. Отправка ответа посетителю остаётся выпуском C. Новый код сам по себе
не включает Owner: ниже — действия Александра в его аккаунтах. Секреты ассистенту
передавать не требуется.

**Миграция `0006_owner_workspace.sql` уже выполнена Александром. Повторять её не
нужно. Новых SQL-скриптов в B.1 нет.** Используется прежняя база `magnt-contacts`.

## 1. Создать приложение входа в GitHub

В GitHub: **Settings → Developer settings → OAuth Apps → New OAuth App**.

| Поле | Значение |
| --- | --- |
| Application name | `MAGNT Owner` |
| Homepage URL | `https://owner.magnt.ru` |
| Authorization callback URL | `https://owner.magnt.ru/callback` |

Сохрани **Client ID**, создай **Client secret**. Секрет понадобится только ядру.
Приложение не запрашивает доступ к репозиториям. Разрешённый GitHub-пользователь —
`redkov-dev`, числовой ID **`264882809`**; имя пользователя не служит проверкой прав.

## 2. Подготовить хранилище OAuth

В Cloudflare **Storage & databases → Workers KV** создай один namespace
`magnt-owner-oauth`. Скопируй его **Namespace ID**. В настройках существующей D1
`magnt-contacts` скопируй **Database ID**. Новую D1 создавать не нужно.

Это идентификаторы ресурсов, не пароли. Они нужны в **Build variables** следующего
Worker; значения не следует заменять названием базы или namespace.

## 3. Создать закрытый Worker `magnt-core`

В **Workers & Pages** создай Worker с импортом существующего GitHub-репозитория
`redkov-dev/cortex`, ветка `main`. Параметры сборки:

| Поле | Значение |
| --- | --- |
| Worker name | `magnt-core` |
| Root directory | `cloudflare/magnt-observer` |
| Deploy command | `npm run deploy:core` |
| Build variable `MAGNT_D1_DATABASE_ID` | Database ID **существующей** `magnt-contacts` |
| Build variable `MAGNT_OAUTH_KV_ID` | Namespace ID нового `magnt-owner-oauth` |

Если первая сборка запустилась до добавления Build variables, добавь их и запусти
повторно. Скрипт намеренно останавливается без ID: он не создаёт пустую замену базы.
Команда использует `wrangler.core.jsonc`; обычная `npx wrangler deploy` для этого
Worker не подходит. Отдельный Build command не требуется.

После сборки проверь **Bindings**: `CONTACTS` указывает на старую базу,
`OAUTH_KV` — на новый namespace. В **Domains & Routes** не должно быть ни доменов,
ни маршрутов; **workers.dev** и **Preview URLs** отключены. Даже при ошибочно
добавленном HTTP-маршруте обычный вход ядра возвращает 404.

В **Settings → Variables and Secrets** ядра добавь значения:

| Имя | Значение / тип |
| --- | --- |
| `OWNER_GITHUB_ID` | `264882809`, обычная переменная |
| `OWNER_GITHUB_CLIENT_ID` | Client ID из GitHub, обычная переменная |
| `OWNER_GITHUB_CLIENT_SECRET` | Client secret из GitHub, **Secret** |
| `OWNER_AUTH_EPOCH` | `1`, обычная переменная |
| `OWNER_MCP_ENABLED` | Пока `false` |
| `OWNER_MCP_WRITE_ENABLED` | Пока `false` |
| `OWNER_DCR_ENABLED` | `false` |
| `CORE_NOTIFICATIONS_ENABLED` | Пока `false` |

Скопируй сюда текущие Telegram-настройки прежнего `magnt-observer`:
`TELEGRAM_BOT_TOKEN` как Secret, `TELEGRAM_OWNER_CHAT_ID`, `NOTIFY_FROM`,
`TELEGRAM_PREVIEW_MODE`, `TELEGRAM_NOTIFICATIONS_ENABLED`,
`TELEGRAM_GOAL_NOTIFICATIONS_ENABLED`; если настроены — `TELEGRAM_MAX_ATTEMPTS`
и `TELEGRAM_RETRY_DELAYS_SECONDS`. Сохрани прежние значения, особенно chat ID
и `NOTIFY_FROM`. Кавычки вокруг значений в панели не нужны.

До шага 6 уведомления отправляет прежний Worker. В ядре отправка дополнительно
закрыта `CORE_NOTIFICATIONS_ENABLED=false`.

## 4. Создать внешний Worker `magnt-owner-gateway`

Импортируй тот же репозиторий и `main`, Root directory тот же.
Имя Worker — **`magnt-owner-gateway`**, Deploy command — **`npm run deploy:owner`**.
Ядро должно уже существовать. Конфигурация создаёт:

- Custom domain **`owner.magnt.ru`** на имеющемся домене;
- Service Binding `OWNER_CORE` → `magnt-core`, entrypoint **`OwnerApi`**;
- два Rate Limiting binding: `OWNER_REQUEST_LIMIT` и `OWNER_LOGIN_LIMIT`.

У этого Worker нет D1, KV, GitHub- и Telegram-секретов. `workers.dev` и Preview
URLs отключены. Проверь, что публичный `magnt-observer` не имеет перекрывающего
маршрута `*.magnt.ru/*`: ему нужны только `magnt.ru/*` и `www.magnt.ru/*`.
Не добавляй к `/mcp` и `/oauth/token` CAPTCHA или браузерную проверку.

## 5. Подключить ChatGPT и проверить права

В **ядре** установи `OWNER_MCP_ENABLED=true`, сохрани с развёртыванием.
`OWNER_MCP_WRITE_ENABLED` пока остаётся `false`.

Создай личное MCP-приложение в ChatGPT:

- название: **MAGNT Owner**;
- URL: **`https://owner.magnt.ru/mcp`**;
- авторизация: **OAuth**;
- ручные Client ID / Client secret для ChatGPT не нужны при автоматической
  регистрации. **GitHub Client secret сюда не вставлять.**

Основной путь использует документ клиента ChatGPT (CIMD), без открытой регистрации.
Если ChatGPT сообщает именно об отказе регистрации клиента (`/oauth/register`,
403), временно включи `OWNER_DCR_ENABLED=true` в ядре, повтори подключение и после
успеха верни `false`. Зарегистрированный клиент продолжит входить и обновлять
токены. Поддерживаются оба пути; не оставляй регистрацию открытой без необходимости.

На странице MAGNT подтверди доступ, оставив возможность автоматического
обновления, затем один раз войди в разрешённый GitHub-аккаунт. Это личное
приложение: не публикуй и не предоставляй подключение другим людям.

Проверки:

1. В ChatGPT попроси: «Покажи новые цели агентов через MAGNT Owner». Затем открой
   одну запись. Чтение не должно автоматически отмечать её просмотренной.
2. Попробуй сохранить свой тестовый черновик: при выключенной записи ожидается
   отказ. После этого включи **в ядре** `OWNER_MCP_WRITE_ENABLED=true`, повтори
   команду, проверь сохранённый текст в новом чате. Черновик никому не отправляется.
3. Без авторизации `owner.magnt.ru/mcp` должен отвечать 401; другой GitHub-аккаунт
   не должен получить доступ. `magnt.ru/mcp-owner` остаётся закрытым (503).
4. Позднее, после истечения часового access token, повтори чтение через ChatGPT:
   оно должно обновить доступ без нового входа в GitHub. Это обязательная проверка
   реального клиента; локальные тесты не заменяют её.

## 6. Переключить публичный MCP и уведомления на ядро

Сначала сохрани прежние Telegram-настройки для восстановления. Затем в Builds
существующего **`magnt-observer`** замени Deploy command на **`npm run deploy:public`**
и разверни `main`. Эта конфигурация оставляет только Service Binding
`PUBLIC_CORE` → `magnt-core`, entrypoint **`PublicApi`**. Публичный адрес `/mcp`,
его четыре инструмента, сайт и сохранённые данные остаются прежними.

Проверь успешную сборку и публичное чтение профиля. Проверь **Bindings** публичного
Worker: D1 `CONTACTS` и KV должны отсутствовать; **Cron Triggers** — пусто.
Удаление привязки не означает удаление самой базы. Удали из публичного Worker
старый Telegram secret, Telegram-переменные, `NOTIFY_FROM`, старые `OWNER_*` и
`MAGNT_CORE_ENABLED`, если добавлялись. Они не должны остаться у внешнего входа.

После этого в **ядре** установи `CORE_NOTIFICATIONS_ENABLED=true`. Его минутный
Cron продолжит прежнюю очередь с прежними квитанциями. За время переключения
сообщения сохраняются; допустима задержка уведомлений, а не потеря истории.
Для проверки можно повторить ранее использованный `admin_test` в прежней D1;
один тест должен дать одно тестовое уведомление, не внешнее обращение.

Изоляция считается включённой только после удаления привязок и секретов у
публичного Worker. До этого по умолчанию работает совместимая переходная версия
`wrangler.jsonc` → `src/index.js`; один merge не завершает переход.

## 7. Защита, лимиты и отзыв

Приложение ограничивает Owner-запросы до 180/мин на IP, а вход и регистрацию —
до 10/мин на IP; есть общий для точки Cloudflare лимит начала входа. Лишние
запросы получают 429. Это приблизительные распределённые счётчики, не глобальная
гарантия. Тела запросов ограничены 24 КиБ, разрешены только нужные методы и пути.

Дополнительно можно использовать одну бесплатную WAF Rate Limiting rule в зоне
`magnt.ru`: пути `/authorize`, `/callback`, `/oauth/register`, 10 запросов за
10 секунд на IP, действие Block на 10 секунд. Правило должно оставаться в
доступных Free-полях; если панель предлагает платный вариант, его не подключать.
Базовая DDoS-защита действует на проксируемом домене. Полноценной гарантии
доступности при распределённой атаке и исчерпании бесплатных квот нет.

Используются Workers Free, D1 и KV в пределах бесплатных квот. Проверь реальные
**CPU time**, число Worker-запросов и KV-операций после подключения: для Workers
Free существенен предел CPU 10 мс, для KV — 1000 записей/сутки. Часовой access token
снижает частоту обновлений. Локальные тесты не доказывают укладывание в CPU-квоту.
Если текущая нагрузка не укладывается, приостанови Owner и измерь причину;
автоматический переход на платный тариф не предусмотрен.

Для экстренного закрытия: `OWNER_MCP_ENABLED=false` в ядре и развёртывание.
Для отзыва всех выданных прав: увеличь `OWNER_AUTH_EPOCH`, например с `1` до `2`,
и разверни. После распространения конфигурации прежние токены не дают доступа
и не обновляются; потребуется повторное подключение. Только записи отключаются
через `OWNER_MCP_WRITE_ENABLED=false`. Отзыв GitHub OAuth App сам по себе не
отзывает уже выданные MAGNT-токены: для них применяется epoch/отключение.

После переключения события MCP (`event_type=mcp_request`) выгружаются из
**magnt-core**; статистика сайта остаётся у **magnt-observer**. Существующий
`npm run metrics` понимает эти события и исключает контролируемые проверки.

Журналы Owner содержат тип события, известный путь, статус и длительность;
не содержат текста обращений, токенов, cookies, OAuth-кодов и query string.
Автоматические HTTP invocation logs и трассировки отключены. Отдельные внешние
Logpush/системы журналирования, если включены вручную, нужно проверить отдельно.

Откат Owner — отключение его флага; публичный MCP и Telegram в ядре работают
независимо. При полном откате на прежний монолит сначала останови Cron ядра,
восстанови старые настройки/привязку публичного Worker и его прежнюю команду
развёртывания. D1 и KV не удалять; применённые миграции не откатывать.
