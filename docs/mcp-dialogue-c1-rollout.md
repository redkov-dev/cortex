# MAGNT C.1 — ручное включение переписки

Эта инструкция продолжает уже выполненное развёртывание Owner B.1.
Новых Workers, базы, GitHub OAuth App или Telegram-бота не требуется.
Код по умолчанию сохраняет прежний режим. Токены начнут выдаваться только после
миграции, выкладки и включения трёх флагов в **magnt-core**.

## 1. Подготовить выпуск

Проверь зелёные проверки PR C.1 и слей его в `main`. Внешние шлюзы остаются
прежними: `magnt-observer` с `PUBLIC_CORE → PublicApi`,
`magnt-owner-gateway` с `OWNER_CORE → OwnerApi`. D1 и секреты находятся в ядре.

В Cloudflare открой **Workers & Pages → magnt-core → Settings → Variables and Secrets**.
Добавь обычные текстовые переменные со значением `false`:

| Переменная | Начальное значение |
| --- | --- |
| `DIALOGUE_CREATE_ENABLED` | `false` |
| `DIALOGUE_READ_ENABLED` | `false` |
| `DIALOGUE_WRITE_ENABLED` | `false` |

Если переменных ещё нет, эффект тот же: функция выключена. Кавычки вокруг
значений в панели не нужны. Существующие Owner/OAuth/Telegram-переменные оставь
как есть. Не меняй `NOTIFY_FROM`, chat ID, `OWNER_AUTH_EPOCH` и секреты.

## 2. Выполнить миграцию 0007 один раз

Сначала сохрани доступную точку восстановления/экспорт базы `magnt-contacts`.
В **Storage & databases → D1 → magnt-contacts → Console** проверь:

```sql
SELECT name FROM sqlite_master
WHERE type = 'table' AND name IN ('owner_inbox', 'owner_replies', 'owner_operations',
  'owner_notification_outbox', 'dialogues', 'message_read_receipts');
```

Первые четыре таблицы должны существовать; двух последних до C.1 нет.
Если `dialogues` уже есть, не запускай файл повторно: проверь завершённость
миграции. Она содержит `ALTER TABLE` и предназначена для однократного применения.

Для применения подготовлена отдельная команда **`npm run db:migrate:dialogue`**.
Она выбирает только [0007_dialogues.sql](../cloudflare/magnt-observer/migrations/0007_dialogues.sql),
применяет его через Wrangler migrations и записывает результат в `d1_migrations`.
Миграции 0001–0006 не запускаются заново, даже если ранее ты выполнял их вручную.
При ошибке текущая миграция откатывается целиком
([документация Cloudflare](https://developers.cloudflare.com/d1/wrangler-commands/#d1-migrations-apply)).

Это можно сделать через уже настроенный Cloudflare Builds без локального терминала:

1. В **magnt-core → Settings → Build** оставь **Build command** пустым:
   `deploy:core` сам собирает ядро. Команда `npm run build` здесь запускает пробную
   сборку старой конфигурации `magnt-observer` и вызывает предупреждение об имени Worker.
   В поле **Deploy command** временно поставь
   **`npm run db:migrate:dialogue && npm run deploy:core`**.
2. Открой **magnt-core → Deployments**, прокрути ниже списка версий и нажми
   **View build history**. Найди сборку `main` с коммитом C.1, открой её и нажми
   **Retry build**; та же команда доступна через **⋯** рядом со сборкой.
   Номер **Version ID** в списке Deployments — идентификатор версии Cloudflare,
   он отличается от GitHub commit SHA. **View rollout history** показывает
   историю переключения версий, а журнал сборок находится в **View build history**.
   Существующие Build variables
   `MAGNT_D1_DATABASE_ID` и `MAGNT_OAUTH_KV_ID` уже используются этим Worker.
3. Проверь в логе успешную миграцию **только `0007_dialogues.sql`** и успешную
   выкладку ядра. Если доступ сборки к D1 отклонён, флаги пока не включай:
   используй эту же команду в своём авторизованном Wrangler с доступом к данной D1.
4. Верни Deploy command на **`npm run deploy:core`**.

Не выполняй файл частями через SQL-консоль: он переносит существующие таблицы,
и важен откат всей миграции при ошибке. Не удаляй таблицы вручную.
После успешной сборки проверь через консоль:

```sql
SELECT name FROM sqlite_master WHERE type = 'table' AND name IN
('dialogues', 'dialogue_events', 'dialogue_access', 'dialogue_operations', 'message_read_receipts');
PRAGMA table_info(owner_inbox);
PRAGMA foreign_key_check;
```

Ожидаются пять новых таблиц, столбцы `latest_incoming_sequence` и
`acknowledged_sequence`; `foreign_key_check` — без строк. Старые обращения,
черновики и квитанции Telegram должны остаться на месте.

## 3. Развернуть ядро

В **magnt-core → Deployments → View build history** разверни `main` с коммитом C.1.
Если предыдущий шаг завершился успешной миграцией и строкой
`Deployed magnt-core triggers`, ядро уже развёрнуто: повторная сборка не нужна.
Root directory остаётся `cloudflare/magnt-observer`, **Build command** пустой, Deploy command —
**`npm run deploy:core`**. Проверь успешную сборку и сохранение прежних D1/KV
bindings. Конфигурация добавляет три Rate Limiting binding:

| Binding | Настроенный лимит |
| --- | --- |
| `DIALOGUE_REQUEST_LIMIT` | 120 запросов за 60 секунд по публичному IP |
| `DIALOGUE_READ_LIMIT` | 30 чтений за 60 секунд по доступу |
| `DIALOGUE_WRITE_LIMIT` | 10 записей за 60 секунд по доступу |

У ядра по-прежнему нет публичных маршрутов, workers.dev и preview URLs.
Дополнительные шлюзы и переключение Cron для C.1 не нужны. Если GitHub Builds
автоматически развернул ядро сразу после merge, достаточно проверить его коммит
и bindings; повторная выкладка того же коммита не требуется.
Лимиты Cloudflare приблизительные и применяются по месту выполнения запроса;
это защита от частого опроса, а не строгая глобальная квота.

## 4. Включить чтение, запись, затем выдачу токенов

В переменных **magnt-core** последовательно установи и сохрани с развёртыванием:

1. `DIALOGUE_READ_ENABLED=true`.
2. `DIALOGUE_WRITE_ENABLED=true`.
3. `DIALOGUE_CREATE_ENABLED=true`.

`OWNER_MCP_ENABLED` и `OWNER_MCP_WRITE_ENABLED` должны уже быть `true` для
публикации. Публичный MCP теперь объявляет шесть инструментов, Owner — пять.
В [ChatGPT Plugins](https://chatgpt.com/plugins) открой подключение **MAGNT** и
нажми **Refresh / Обновить**. Повтори для **OWNER_M**. Проверь появление
`get_dialogue` и `send_dialogue_message` у MAGNT, `manage_dialogue_access` у Owner;
также обновляются описания существующих инструментов. Для контрольного вызова
используй новый чат с обновлёнными подключениями
([инструкция OpenAI](https://developers.openai.com/plugins/deploy/connect-chatgpt#refresh-metadata)).
Новые OAuth scopes не
требуются. После включения полное чтение через Owner ставит отметку «прочитано».

## 5. Проверить на одной тестовой переписке

В публичном MAGNT попроси: «Отправь тестовое обращение `C.1 проверка обмена`
с `is_test=true` и новым `submission_id`. Сохрани выданный токен приватно».
Токен не вставляй в GitHub, Telegram, URL, общую память или текст сообщения.

1. В квитанции должны быть токен, `message_id`, `read_status=unread` и совет
   вернуться через час. Для проверки ждать час не нужно.
2. В Owner попроси **показать список тестовых входящих**, не открывая беседу.
   Публичный `get_dialogue` должен вернуть `message=null` и статус входящего
   `unread`. Запиши текущую ревизию из списка.
3. Дай Owner явную команду опубликовать в этой тестовой беседе текст
   «Ответ C.1 получен». Публикация должна пройти без открытия входящего.
4. В публичном MAGNT вызови `get_dialogue` с сохранённым токеном. Он должен
   вернуть ровно один ответ и по-прежнему `sent_message.read_status=unread`.
   В Owner последнее исходящее теперь имеет статус `read` и время.
5. Открой входящее полностью через Owner. Повторная публичная проверка с
   `next_cursor` возвращает `message=null`, но уже `sent_message.read_status=read`.
6. Отправь по тому же токену одно продолжение. Оно появляется в той же карточке
   Owner, возвращает её в требующие внимания и сначала остаётся непрочитанным.
7. В новом чате/сеансе публичного клиента используй сохранённые токен и курсор.
   Доступ должен сохраниться. Повтор с прежним курсором возвращает прежний
   ответ, что позволяет восстановиться после потери сетевого результата.

Тестовая переписка наследует `is_test=true`: обычные входящие и Telegram не
пополняются тестовыми сообщениями. Локальные тесты отдельно проверяют отправку
нетестовых уведомлений через подменённый Telegram API.

## 6. Старые обращения и остановка

У Николая, Андрея и других прежних отправителей токенов автоматически не
появится. Либо они создают новое обращение и сохраняют токен, либо ты явно
выполняешь `manage_dialogue_access(action=enable)` для нужного старого контакта
и передаёшь токен проверенному получателю по известному каналу. Старые тексты и
черновики при этом не публикуются. Потерянный токен перевыпускается через
`rotate`; старый перестаёт работать. `revoke` закрывает доступ без удаления истории.

Чтобы остановить новые обращения с токенами, поставь `DIALOGUE_CREATE_ENABLED=false`.
Чтобы временно остановить продолжения и публикации, дополнительно поставь
`DIALOGUE_WRITE_ENABLED=false`. **Чтение оставь включённым**, чтобы уже получившие
токены могли забрать опубликованные ответы. Владелец при этом может отзывать доступ.
`DIALOGUE_READ_ENABLED=false` закрывает весь публичный обмен; используй его при
необходимости полной остановки. Owner в этом режиме показывает исходные
обращения и частные черновики; страницы завершаются, даже если в последовательности
есть временно скрытые события диалога. Полная переписка снова видна после включения
чтения. Не удаляй новые таблицы и не откатывай схему:
флаги выключают функцию с сохранением данных.
